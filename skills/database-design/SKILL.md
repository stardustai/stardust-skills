# 数据库选型与表结构设计

## 目标

选择能够满足真实负载、同时维护成本最低的持久化架构。根据用户的数据库能力调整提问和解释方式，但数据完整性、安全、迁移、文档和索引标准必须由项目风险决定，不能由用户岗位或回答长短决定。使用满足当前任务的最小输出展示结论，避免让简单选型被完整工程报告淹没。

## 不可妥协的规则

- 分开判断用户能力和项目成熟度。用户不懂技术，不代表可以降低工程保护标准。
- 分开判断项目等级和输出深度。“精简”只能压缩展示内容，不能省略实际适用的完整性、安全、注释和索引标准；“完整”也不得填充与任务无关的章节。
- 使用仓库信息前，先确认当前仓库确实属于用户所说的项目。不得把独立或假设性需求绑定到任意工作目录。
- 仓库在范围内时，先检查已有数据库依赖、ORM、迁移工具、部署清单、运行环境和命名约定，再向用户提问。不得暴露密钥值。
- 已有数据库能够满足需求时，优先沿用。只有收益有需求证据支撑，并且大于迁移和运维成本时，才建议更换。
- 讨论缓存、搜索引擎、向量库、队列或分析副本前，先确定权威数据源。
- Demo 和普通应用优先只使用一个主数据库。增加第二种存储时，必须说明具体负载以及同步、故障、恢复和数据归属规则。
- 需求不明确，或者业务包含事务、约束和关系时，优先使用团队熟悉的关系型数据库。不得仅因为“结构以后可能变化”就选择 NoSQL。
- 不得根据假想的未来规模选技术。改为给出可度量的升级触发条件。
- 未识别核心实体和主要读写查询前，不生成最终 DDL。关键上下文缺失时，明确列出保守假设。
- 不得把举例时的假设写成用户需求。在 Schema 或 DDL 前单独列出“假设”。
- 输出厂商专属 SQL 前，声明目标引擎、SQL 方言和版本依据。涉及版本差异时，核对官方文档。
- 每张表和每个字段都必须有明确、可理解的名称和描述。不得让读者猜测 `data`、`value`、`type`、`status`、`info` 等字段的含义。
- 目标数据库支持原生表和字段注释时，数据字典不能替代原生注释。PostgreSQL 或 MySQL DDL 缺少可持久化表注释或字段注释时，视为未完成。
- 明确主键、可空性、默认值、唯一性、检查约束、外键以及删除和更新行为。
- 根据查询设计索引。每个非约束索引都要对应筛选、关联、排序、聚合或分页需求，并解释字段顺序。
- 将索引标记为：约束必需、基于查询推理、执行计划已验证或生产观测已验证。基于推理的索引不得称为“必须”或“最优”。
- 不得重复创建主键或唯一约束已经提供的索引。非显然索引要说明读性能收益和写入、存储成本。
- 没有代表性数据和实际执行计划时，不得声称性能已经验证。
- 表和字段注释不得包含凭据、密钥、个人数据或敏感运维信息。
- 不要为了展示本 Skill 的工作过程而机械输出分类标签、完整检查清单或所有中间推理。只展示会帮助用户决策、实施或验证的内容。
- 尊重任务范围。用户只要求分析或审查时，不修改文件；只有用户要求实现时，才修改迁移或应用代码。

## 工作流程

### 1. 确认上下文范围

根据用户描述、引用文件、任务历史和仓库关系判断范围。只有用户明确提到当前项目或上下文能够证明关联时，才把仓库作为证据。如果仓库是否相关不明确，而且会实质改变选型，提出一个简短的范围问题，或分别列出不同假设；不得默认采用当前工作目录的技术栈。

仓库在范围内时，只检查识别以下信息所需的文件：

- 语言、框架、ORM 和迁移工具；
- 已有数据库引擎和 Schema 约定；
- 部署拓扑和托管服务；
- 业务实体和已有查询、API 模式；
- 能体现完整性要求的测试或文档。

明确区分仓库证据、用户陈述和模型假设。独立业务场景中不得暴露无关仓库信息。

### 2. 从独立维度分析任务

先尝试推断，再向用户提问。记录：

- 解释模式：`business`、`builder` 或 `engineer`；
- 项目等级：`demo`、`prototype`、`production` 或 `critical`；
- 输出深度：“精简”或“完整”；
- 数据敏感度：公开、内部、个人、财务、凭据、受监管；
- 工作负载：事务、分析、搜索、缓存、队列或流、时序、向量、本地嵌入式；
- 运维负责人和可用的数据库经验。

输出深度按照以下规则判定：

- 用户明确要求“简短”“只给结论”时使用“精简”；明确要求详细设计、完整方案或上线检查时使用“完整”。
- 只做数据库选型、方案比较或回答一个局部问题时，默认“精简”。
- 生成或审查 Schema、DDL、索引、迁移文件时，默认“完整”；用户要求简短时可以压缩解释，但不能删减 DDL 必需的名称、注释、约束和索引依据。
- 项目风险只决定工程保护标准，不自动决定回答长度。Production 可以使用“精简”，Demo 也可以因为要求完整 DDL 而使用“完整”。
- 无需向用户询问输出深度；根据请求推断，用户可以随时覆盖。

每次最多询问三个真正影响数据库决策的问题。使用用户能理解的表达，例如问“是否会有多人同时修改同一条记录”，不要直接要求用户解释隔离级别或基数。无法获得答案但风险可控时，带着显式假设继续。

### 3. 建立负载和查询清单

记录真正影响设计的操作：

- 最频繁和延迟最敏感的读取；
- 写入路径、事务、幂等和并发；
- 筛选、关联、排序、聚合、分页和唯一性规则；
- 当前规模、可信增长范围、保留、归档和删除；
- 一致性、可用性、恢复、地域和合规要求。

不得编造精确规模。使用范围，或者标记为未知。

### 4. 选择持久化架构

按照以下顺序决策：

1. 权威数据源；
2. 数据模型适配性和事务边界；
3. 数据库引擎适配性；
4. 部署方式和运维负担；
5. 只有确有必要时才增加辅助存储。

给出一个推荐方案，最多两个真正可行的备选方案。解释有诱惑力但未选择的方案、主要取舍、迁移风险、必要时的厂商锁定，以及可度量的重新评估条件。数据库引擎选型与云厂商、托管产品选型分开处理。

### 5. 设计 Schema

写 SQL 前，先建模实体、生命周期、归属、关系、不变量和删除语义。然后根据选定方言定义名称、类型、主外键、约束、时间字段、敏感数据处理和描述。

数据库支持原生 Schema 注释时，输出可持久化的表注释和字段注释。不支持适合的原生注释时，输出结构化数据字典和清晰的源码注释，并明确源码注释不是可查询的元数据。

### 6. 根据查询设计索引

将每个重要查询映射到已有约束索引或候选索引。考虑区分度、等值或范围条件、排序方向、前导列、覆盖需求、写入频率和表规模。避免猜测性索引和“每列一个索引”。

只有存在代表性数据时才建议执行计划验证。否则将索引标记为“基于查询推理，尚未验证”。

### 7. 增加工程保护

对于非 Demo 或使用真实数据的系统，覆盖迁移、回滚或前滚、备份恢复测试、最小权限、连接管理、监控、保留、审计、租户隔离和破坏性变更策略。没有需求证据时，不增加高可用、分区、分片或副本。

### 8. 输出并验证

遵循 [references/output-contract.md](references/output-contract.md)。先应用项目等级对应的工程标准，再应用输出深度决定展示范围：“精简”给出足以安全决策或使用产物的最小内容，“完整”给出任务所需的完整设计与验证信息。`business` 模式先给通俗结论和数据字典，再给 SQL；`builder` 模式突出可直接使用的迁移和集成提示；`engineer` 模式补充事务、执行计划、容量和运维分析。

DDL 写入文件后，从本 Skill 目录解析 `scripts/validate_ddl.py` 的路径并运行：

```bash
python3 scripts/validate_ddl.py path/to/schema.sql --dialect postgresql --level production
```

使用真实方言和项目等级。修复错误，根据需求审查警告，并说明哪些内容已经验证、哪些仍未验证。该脚本只是质量护栏，不是完整 SQL 解析器、负载基准测试，也不能替代数据库或迁移工具验证。

DDL 只出现在回答代码块、没有写入文件时，也要手工执行同等标准检查，尤其确认原生表注释、字段注释、主键、可空性和索引依据齐全。

## 完成门槛

完成前确认：

- 推荐结论能够追溯到明确证据和假设；
- 工程标准由数据和项目风险决定，而不是由用户岗位决定；
- 每张表和每个字段都有名称和描述；
- 支持原生注释的数据库已经在 DDL 中持久化表说明和字段说明；
- 可落入数据库的完整性规则尽量由约束实现，而不是只写在应用说明里；
- 每个候选索引都能对应查询，并且没有明显重复；
- 方言专属 DDL 内部一致；
- 生产级结论包含迁移和运维影响；
- 输出深度与请求匹配，精简输出没有降低工程标准，完整输出没有堆积无关章节；
- 未确认信息和验证边界清晰可见。

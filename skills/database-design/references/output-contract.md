## 输出深度

输出深度只控制展示范围，不控制工程标准。先按项目等级和数据敏感度完成判断，再选择“精简”或“完整”。

### 精简输出

适用于数据库选型、方案比较、单一局部问题，或者用户明确要求简短回答。

只展示完成当前任务需要的最小内容：

1. 一个明确结论；
2. 两到四条真正改变决策的依据；
3. 会改变结论的关键假设、风险或升级触发条件；
4. 用户要求产物时，提供完整可用的产物，而不是删减版 DDL。

不要机械展示“用户画像”“工作负载分类”“十项检查结果”等内部分析标签。没有实质性备选方案时，不为凑格式罗列备选数据库。Production 或 Critical 项目使用精简输出时，仍要简洁指出当前任务不能覆盖的上线验证边界。

### 完整输出

适用于生成或审查 Schema、DDL、索引、迁移，详细设计，生产上线检查，或者用户明确要求完整方案。

根据任务选择以下适用部分，不要求所有部分机械出现：

1. **推荐结论**：一个主要选择和简洁结论。
2. **证据和假设**：只列影响设计的仓库证据、用户陈述和模型假设。
3. **决策依据**：需求到能力的推导、成本、被拒绝方案和重新评估条件。
4. **数据模型和数据字典**：实体、关系、规则以及表和字段含义。
5. **DDL 或迁移**：引擎、方言、版本依据和可执行产物。
6. **索引与查询映射**：每个非约束索引对应的查询、字段顺序、成本和验证状态。
7. **工程保护**：与项目等级相匹配的迁移、恢复、权限、监控和部署影响。
8. **验证和未解决风险**：实际检查、尚未完成的检查和待确认问题。

不要把推荐结论埋在大段 SQL 后面，也不要展开与用户任务无关的章节。

## 所有输出的共同底线

除非仓库已经确认属于用户所说的项目，否则不得引用或依赖仓库信息。假设性示例必须明确标为假设。

无法获得答案而继续时，在模型或 DDL 前明确增加“假设”部分。精简输出只列会改变结论的假设。不得把直属主管审批、支持半天假、软删除或全局唯一等常见举例默认为已确认需求。

## 只做数据库选型时的输出

用户只要求数据库选型时，提供：

- 一个推荐方案；
- 为什么适合当前团队和运维条件；
- 实质性缺点；
- 有实质意义时，最多两个备选方案以及没有选择的原因；
- 会改变当前选择的升级或重新评估条件。

“精简”默认使用一个短段落或少量要点，不输出数据字典、DDL、完整生产清单或内部分类标签。“完整”才展开工作负载、迁移成本、运维责任和验证边界。

除非解释选型需要，不生成猜测性表结构。

## Schema 和 DDL 输出

SQL 前先提供数据字典：

| 项目 | 必填内容 |
|---|---|
| 表名 | 精确 SQL 名称 |
| 表用途 | 业务责任以及每行记录代表什么 |
| 字段名 | 精确 SQL 名称 |
| 类型 | 目标方言中的类型 |
| 必填和默认值 | 可空性和默认值语义 |
| 字段说明 | 含义、单位或格式、允许值、空值含义、敏感度 |
| 完整性 | 主键、外键、唯一、检查或生命周期规则 |

DDL 必须包含：

- 明确的数据库引擎、方言和版本依据；
- 仓库约定需要时使用 Schema 限定名；
- 主键、可空性、默认值、唯一性、检查约束和外键；
- 有意识选择的外键更新和删除行为；
- 数据库支持时使用原生表注释和字段注释；
- 有必要时使用稳定的约束名和索引名；
- 使用 `-- 支持：` 等源码注释说明索引目的；
- 不包含示例密钥或真实个人信息。

数据库没有合适的原生表和字段注释时，同时提供数据字典和清晰源码注释，并说明这些注释不是可持久化、可查询的元数据。

数据字典用于帮助人理解，不能替代数据库原生注释。PostgreSQL 必须输出 `COMMENT ON TABLE` 和每个字段的 `COMMENT ON COLUMN`；MySQL 必须使用目标版本支持的表和字段 `COMMENT`。缺少任何一项时，DDL 不得标为完成。

分开提供：

- 全新安装 Schema；
- 增量迁移；
- 种子或 Demo 数据；
- 回滚或前滚说明。

不得把全新建库 DDL 当成安全的生产迁移。

“精简”只能压缩 DDL 前后的解释，不能省略数据字典、原生表和字段注释、关键约束、必要索引依据以及方言声明。“完整”根据项目等级补充迁移、回滚、权限、恢复和验证细节。

## 审查输出

按照影响程度列出可执行问题：

- 正确性和数据丢失风险；
- 安全、隐私和租户隔离风险；
- 缺失的完整性约束；
- 迁移和可用性风险；
- 缺失或有害索引；
- 可维护性和文档问题。

每个问题给出证据、后果和具体修复方式。区分已经确认的缺陷和依赖负载的问题。没有可执行问题时，明确说明，并列出剩余验证边界。

审查默认使用“完整”。用户明确要求简短时，可以只列高优先级问题，但不得把未展示的问题表述为不存在；说明审查范围和剩余边界。

## 不同受众的输出顺序

### 业务模式（business）

顺序：推荐结论 → 业务对象和规则 → 数据字典 → 风险 → 可选技术附录。

用重复记录、状态不一致、跨客户数据泄露或无法恢复数据等业务后果进行解释。

### 构建模式（builder）

顺序：推荐结论 → 假设 → 搭建和迁移产物 → 数据字典 → 索引和查询示例 → 生产升级提示。

产物要可直接复制，同时明确占位符和环境相关值。

### 工程模式（engineer）

顺序：推荐结论 → 证据和负载 → 事务和模型 → DDL 和迁移 → 索引与查询分析 → 执行和运维验证。

简洁暴露取舍和不确定性。

## 最终验收清单

所有适用项通过后才能完成：

- [ ] 推荐结论来自明确的负载和团队约束。
- [ ] 已区分权威数据源和辅助存储。
- [ ] 已分别记录项目等级和数据敏感度。
- [ ] 已选择与请求匹配的输出深度，并且没有用精简输出降低工程标准。
- [ ] 已明确引擎、方言和版本依据。
- [ ] 每张表都有有意义的名称和说明。
- [ ] 每个字段都有有意义的名称和说明。
- [ ] 主键和业务自然唯一性已经强制实现。
- [ ] 可空性、默认值、检查约束、外键和生命周期行为已经明确。
- [ ] 金额、时间、状态、JSON、个人数据和租户边界语义经过设计。
- [ ] 每个二级索引都对应查询，并说明成本和验证状态。
- [ ] 没有重复创建约束已经提供的索引或其他重复索引。
- [ ] 生产级工作包含迁移、恢复、权限和监控影响。
- [ ] 验证声明与实际完成的检查一致。
- [ ] 假设、开放问题和升级触发条件清晰可见。

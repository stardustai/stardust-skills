## 先建模再写 SQL

为每个实体确认：

- 业务用途和负责人；
- 从创建到删除或归档的生命周期；
- 权威字段和派生字段；
- 关系和允许的基数；
- 即使应用出现 Bug 或并发写入也必须成立的不变量；
- 常见查询和更新路径。

不要把每个 UI 组件或 API 响应都建成一张表。不要为了少写关联而把无关实体塞进同一张表。

## 命名和描述

- 采用一种一致的命名方式。为提高 SQL 可移植性，默认使用不加引号的 `snake_case`。
- 表名描述稳定的业务实体或事件，不使用页面名称。
- 字段名要体现单位和语义，例如 `amount_minor`、`expires_at`、`is_active`、`status_code`。
- 避免没有解释的通用字段名，例如 `data`、`value`、`type`、`status`、`info`、`extra`、`ext`、`flag` 和数字编号字段。
- 每张表都给出简短用途说明。
- 每个字段都说明业务含义、单位或格式、允许值、空值含义，以及必要时的数据敏感度。
- 描述要长期有效，不写工单号、临时实现备注、凭据或个人数据。
- 数据库或迁移工具需要稳定名称时，统一命名约束和索引。

## 主键、唯一性和关系

- 每张持久化表都要有主键。关联表可以使用复合主键，或者使用有充分理由的代理主键并补充唯一约束。
- 有意识地选择主键策略。考虑是否对外暴露、离线生成、分布式生成、索引局部性和 ORM 支持，不要条件反射地选择 UUID 或自增整数。
- 即使已有代理主键，也要用 `UNIQUE` 约束保护业务自然唯一性。
- 当数据库负责关系完整性，并且运维模型支持时，建立外键。
- 明确 `ON DELETE` 和 `ON UPDATE` 行为。没有生命周期分析时，不使用大范围级联删除。
- 禁止逗号分隔 ID 和未经校验的多态外键。
- 有顺序的关系使用明确位置字段，并定义唯一性边界。
- 多租户业务唯一性属于租户范围时，把租户边界加入唯一约束。

## 类型和业务语义

### 金额和计量值

- 金额不得使用浮点类型。
- 使用明确精度和小数位的精确小数，或者最小货币单位整数；存在多币种时保存币种。
- 时长、大小、比例和度量值在字段名或说明中标明单位。

### 时间

- 区分时间点、日历日期、本地时间、时长和周期计划。
- 现实世界时间点使用目标数据库支持的时区安全语义，展示时再转换。
- 本地计划时间明确时区假设。
- 只有生命周期确实需要时才增加 `created_at` 和 `updated_at`，并说明由谁更新。

### 文本、标识和二进制数据

- 根据业务规则或数据库语义选择长度，不要机械使用 `VARCHAR(255)`。
- 只有业务身份不区分大小写时才统一大小写，并在所有入口一致执行。
- 适合时把大文件放在对象存储，只在数据库保留元数据和对象引用。
- 描述性元数据中不得出现原始凭据或密钥。

### 状态和枚举

- 定义合法状态以及谁负责状态迁移。
- 根据变化频率和方言迁移成本，选择检查约束、字典表或原生枚举。
- 生命周期超过两种有意义状态时，不使用布尔值代替状态。
- 明确空值含义，不能让 `NULL` 成为未记录的额外状态。

### JSON 和灵活属性

- JSON 用于真正可变、嵌套或由外部定义的数据，不用于逃避已知字段建模。
- 描述预期结构和数据归属。
- 经常参与筛选、关联、约束或唯一识别的属性，应尽量提升为有类型字段。
- 定义校验、索引、迁移和大小边界。

## 约束和生命周期

- 每个字段都明确可空性，不依赖 SQL 默认可空行为。
- 稳定不变量尽量使用主键、唯一、外键和检查约束实现。
- 只有数据库在不了解调用方隐含上下文时仍能正确选择值，才设置默认值。
- 软删除是一种业务生命周期能力，不是默认字段。定义唯一性、查询可见性、恢复、保留和最终删除规则。
- 只有并发更新行为确实需要时才增加乐观锁版本字段。
- 需要追责时，审计历史与普通时间戳分开，记录操作者、动作、前后值和原因。
- 避免应用迁移无法复现或测试的数据库隐式行为。

## 敏感数据和租户数据

- 对敏感字段分类并遵循最小收集原则。
- Schema 注释、日志、种子数据和索引名中不得放敏感值。
- 定义保留、访问、导出、更正和删除要求。
- 租户表要明确数据归属、租户范围唯一性、查询过滤和支撑索引。
- 未实际验证策略和绕过路径前，不得声称行级安全或应用过滤已经实现租户隔离。
- 认证凭据和个人资料分开；保存密码校验值，不保存明文密码。

## 不同方言的注释方式

### PostgreSQL

使用可持久化元数据：

```sql
COMMENT ON TABLE app_user IS '已注册的应用账号。';
COMMENT ON COLUMN app_user.email IS '标准化后的登录邮箱；有效账号范围内唯一。';
```

每张表和每个字段都要注释。连接到数据库的用户可能能够读取注释，因此不得写入密钥或个人值。

### MySQL

使用目标版本支持的字段和表 `COMMENT`：

```sql
CREATE TABLE app_user (
  id BIGINT NOT NULL COMMENT '账号内部标识',
  PRIMARY KEY (id)
) COMMENT='已注册的应用账号';
```

检查目标版本的长度限制和语法。

### SQLite

SQLite 没有与 PostgreSQL、MySQL 等价且可移植的持久化表和字段注释机制。同时输出结构化数据字典和清晰源码注释：

```sql
-- 表 app_user：已注册的应用账号。
CREATE TABLE app_user (
  -- 字段 id：账号内部标识。
  id INTEGER PRIMARY KEY NOT NULL
);
```

不得声称这些源码注释是数据库中可查询的 Schema 元数据。

## 反模式

拒绝或明确论证以下设计：

- 缺少表说明或字段说明；
- 名称模糊、无法体现业务含义；
- 日期、数字或 ID 以未校验自由文本保存；
- 金额使用 `float` 或 `double`；
- 使用逗号分隔关系 ID；
- 用一个 JSON 或 Blob 字段装下整个业务领域；
- 所有字段都可空；
- 只有代理主键，没有自然唯一性；
- 自动增加时间戳、软删除或审计字段，却没有定义行为；
- 唯一性只在应用中检查，无法抵抗并发；
- 把跨方言的“通用 SQL”当成可直接执行的 SQL；
- 把破坏性迁移隐藏在全新建表脚本中。

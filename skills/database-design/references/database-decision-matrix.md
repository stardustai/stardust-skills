## 决策顺序

根据需求而不是流行度进行决策：

1. 确定权威数据源。
2. 确定事务、不变量和关系形态。
3. 确定主要读写和分析负载。
4. 能够满足需求时，复用组织已经支持的技术栈。
5. 选择数据库引擎类型。
6. 选择自建还是托管部署。
7. 只有主数据库无法满足有测量依据或强证据支撑的需求时，才增加辅助存储。

## 默认护栏

- 优先选择团队已支持的数据库，而不是理论上更理想但无人熟悉的数据库。
- 需求不完整、关系重要或多条记录必须原子修改时，优先关系型数据库。
- 生产项目缺少数据库运维能力且预算允许时，优先托管服务。
- Demo 和普通应用只使用一个主数据库。
- 不得因为猜测未来规模就选择分布式数据库、分片或双活架构。
- 未分析持久性、一致性、恢复和查询模型前，不得把 Redis、搜索引擎、对象存储或队列当成权威数据源。
- 主数据库已有向量能力并满足实际规模和延迟时，不额外增加独立向量库。
- 不得为了逃避 Schema 设计或迁移而选择文档数据库。
- 不得把 Serverless 托管方式和数据库模型混为一谈。分别评估连接行为、限制、冷启动、价格和运维责任。

## 引擎适配性

### SQLite

适合：

- 嵌入式、设备本地、桌面、CLI、测试、教学和可丢弃 Demo；
- 单应用进程或低写并发；
- 单文件和极低运维成本本身就是优势。

不适合或需要谨慎：

- 多个独立网络客户端直接访问同一个文件；
- 持续并发写入或多实例 Web 应用写入；
- 本地行为必须高度还原另一种生产数据库。

生产将使用 PostgreSQL 或 MySQL 时，说明类型、并发、迁移和 SQL 语义差异。如果一致性比搭建速度更重要，本地也使用目标生产引擎。

### PostgreSQL

常见适用场景：

- 包含关系、事务和约束的业务应用；
- 关系数据与受控 JSON 混合；
- 复杂查询、报表、全文检索、地理或向量扩展仍可由一个运维系统承担；
- 团队需要标准化 SQL 和丰富索引能力。

需要检查：

- 团队和托管平台是否支持；
- 目标托管服务是否允许所需扩展；
- 版本专属 SQL 和在线迁移要求。

### MySQL 及兼容托管版本

常见适用场景：

- 团队已有 MySQL 经验、工具、托管平台或组织标准；
- 常规 Web OLTP 负载；
- 应用生态和迁移已经基于 MySQL 语义。

需要检查：

- 精确引擎和版本行为、SQL Mode、排序规则、JSON 和索引能力，以及托管产品差异；
- 建议在 PostgreSQL 与 MySQL 之间切换前，先计算迁移成本。

### MongoDB 等文档数据库

至少需要以下证据：

- 聚合文档通常一起读取和更新；
- 内嵌边界稳定，文档增长有上限；
- 灵活结构来自业务本身，而不是为了逃避建模；
- 事务、关联、唯一性和报表需求与文档模型兼容。

如果跨文档不变量、复杂关系查询和关系型报表占主导，应拒绝或明确限制该方案。

### Redis

优先作为缓存、限流、临时协调、队列或流、计数器和特殊低延迟数据结构的辅助存储。

作为权威数据源前，必须说明：

- 持久化模式；
- 可接受的数据丢失窗口；
- 内存和淘汰策略；
- 复制、故障切换和恢复行为；
- 查询和关系能力限制；
- 每类 Key 的权威归属。

### 搜索引擎

用于明确的全文相关性、分面搜索、日志或事件检索，或者主数据库无法满足的搜索延迟和功能。

除非产品本身就是经过专门耐久性设计的搜索或日志平台，否则权威记录保留在其他系统。明确摄取延迟、重放、删除传播、Mapping 演进和降级行为。

### 分析型和列式数据库

用于追加型事件、大范围扫描、聚合和分析并发，并且 OLTP 数据库无法经济地承担这些工作时。

明确权威数据归属、数据摄取、迟到数据、去重、保留和对账。几个普通后台报表不足以证明需要新增分析数据库。

### 时序和向量专用数据库

只有通用数据库及其扩展无法满足时才选择，例如已有测量结果证明规模、保留或降采样、索引大小、延迟、过滤或运维隔离不满足要求。

## 辅助存储准入条件

每增加一种存储，都回答：

- 它服务于哪条具体查询或运维需求？
- 为什么主数据库无法在可接受范围内满足？
- 每个重复字段以哪个系统为准？
- 数据如何同步、重放、修复和删除？
- 辅助系统不可用或数据滞后时会怎样？
- 谁负责运维和成本？
- 什么指标触发引入，什么指标允许移除？

缺少这些答案时，继续使用主数据库。

## 推荐结论所需证据

输出：

- 一个推荐引擎和部署方式；
- 需求到能力的推导；
- 与用户和团队运维能力的匹配；
- 实质性缺点和故障模式；
- 最多两个真正可行的备选；
- 为什么没有选择看似诱人的方案；
- Demo 到生产的迁移影响；
- 哪些假设变化会推翻结论。

不要使用没有依据的数字评分制造虚假精确感。简短的证据表通常更合适。

## 重新评估触发条件

使用可度量条件，不写“以后规模大了再说”，例如：

- 持续写并发超过测试上限；
- 查询和索引调优后，p95 延迟仍不达标；
- 数据或索引工作集超过约定容量；
- 报表扫描干扰事务延迟；
- 搜索相关性或分面能力超过主数据库能力；
- 恢复测试无法满足 RPO 或 RTO；
- 合规或数据地域要求变化；
- 运维负责人或组织标准平台变化。

## 从查询开始

建立索引前，整理重要查询模式：

- 等值和范围筛选；
- 关联字段；
- 排序和分页顺序；
- 分组或聚合；
- 唯一性保护；
- 全文、JSON、空间、向量或时序条件；
- 读取频率和延迟重要程度；
- 写入频率和批量写入行为。

不要每个字段都建索引。字段出现在表里本身不能成为建索引的理由。

## 约束自带索引

- 把主键和唯一约束创建的索引视为已有覆盖。
- 目的是保护业务完整性时，优先使用唯一约束，不要创建没有解释的手工唯一索引。
- 避免完全重复的索引。已有索引前缀能够覆盖，而且没有独立查询或物理原因时，不再创建。
- 增加手工索引前，检查 ORM 已生成的索引。

## 联合索引字段顺序

根据实际条件和排序需要确定顺序：

- 相关查询都必须限制租户或分区边界时，将该边界放在前面。
- 常见 B-tree 负载中，通常先放有意义的等值条件，再放范围条件；在等值条件后评估排序和分页需求。
- 不要机械套用口诀。考虑数据库行为、区分度、Skip Scan、排序和其他查询模式。
- 控制联合索引宽度。只有读收益经过测量且写入、存储成本可接受时，才增加 Include 或覆盖字段。
- `(a, b)` 和 `(b, a)` 不是天然等价的索引。

记录能够解释字段顺序的查询模式。

## 区分度和表规模

- 小表全表扫描可能更快、更简单，不需要二级索引。
- 单独对低区分度布尔字段或少量状态值建索引通常收益有限；可以与高区分度条件组合，或在数据库和稳定负载支持时使用部分或过滤索引。
- 只有查询条件与索引条件一致时，才给经常查询的稀疏子集建索引。
- 频繁更新的字段只有读收益足够大时才建索引。
- 评估写放大、存储、内存、Vacuum 或 Compaction，以及迁移时间。

## 特殊索引

只有查询操作符和模式匹配时才使用：

- 全文索引用于语言相关文本搜索；
- 表达式或函数索引用于查询中稳定出现的表达式；
- 部分或过滤索引用于稳定、选择性高的子集；
- JSON 索引用于明确路径和操作符，不能“以防万一”索引整个 JSON；
- 空间、向量、BRIN、GIN、GiST 等索引只有在理解操作符和数据分布假设时使用。

生成特殊索引 DDL 前，核对目标引擎、版本和迁移语法。

## 外键和租户

- 根据关联、父记录更新或删除和锁行为，判断外键字段是否需要支撑索引。小表或只写表不能机械增加。
- 所有查询都要求租户过滤时，在相关联合索引中加入 `tenant_id`。
- 租户范围唯一性要匹配真实身份边界，例如 `(tenant_id, external_id)`。
- 需要防止跨租户关系时，使用复合外键或其他已经验证的强制方案。

## 验证和维护

对重要生产查询：

1. 准备有代表性的数据分布和行数。
2. 使用目标数据库执行计划工具；只有安全时才实际执行查询。
3. 检查扫描行数或页面、排序策略、关联策略、估算偏差和延迟。
4. 对大索引测试写入成本和迁移时间。
5. 上线后监控索引使用情况。
6. 通过经过审查的迁移删除无用或重复索引。

不得仅根据 DDL 声称索引最优。标记为：

- 约束必需；
- 基于查询推理，尚未验证；
- 执行计划已验证；
- 生产观测已验证。

从可能页面或流程推断出的索引使用“候选”或“基于查询推理”。“必须”只用于完整性或约束索引，或者已明确确认并在相应等级完成验证的需求。

## 索引与查询映射表

每个非约束索引都要提供：

| 项目 | 必填内容 |
|---|---|
| 索引 | 稳定的索引名和表名 |
| 查询 | 代表性的筛选、关联、排序或分页模式 |
| 字段 | 按顺序列出 Key，必要时列出 Include 字段 |
| 原因 | 为什么已有索引不能满足 |
| 成本 | 预期写入、存储或迁移代价 |
| 状态 | 基于推理、执行计划已验证或生产观测已验证 |
| 触发条件 | 什么证据会要求修改或删除索引 |

在生成的索引 DDL 前增加就近源码注释，让静态审查能够对应设计意图：

```sql
-- 支持：按创建时间倒序查询某个租户的有效订单。
CREATE INDEX idx_orders_tenant_active_created
  ON orders (tenant_id, created_at DESC)
  WHERE status = 'active';
```

# Harness Dev Flow

从空仓库起步、靠分层 markdown 文档驱动 AI 编码、逐块可重复验收的轻量 agent-first 开发流程。灵感来自 OpenAI《Harness Engineering: leveraging Codex in an agent-first world》——"Humans steer. Agents execute."——适用于单人、低风险原型。

## 公司使用边界

- 用于隔离的 R0 原型或正式立项前的需求、依赖和验收梳理。正式公司项目先走 `spec-intake` 的工程就绪门禁，再由 `vibe-coding` 负责工程交付；本 Skill 的模板不能替代仓库既有规则、架构合同、测试或评审。
- 原型只使用合成数据，不接入生产系统或真实客户资料。需要超出原型边界时，先确定正式 Spec 和交付路径。
- 对已有仓库，遵守其 `AGENTS.md`、文档布局和责任边界，不强制搬迁目录。这里的 `docs/` 结构仅用于新建原型。

## 核心原则

这些原则解释了为什么流程是这个形状，不是常识，删掉任一条都会让 agent 产出明显变差：

1. **原型仓库保留执行事实**。已确认的意图、契约、验收标准落盘进 `docs/` 的版本化 markdown；外部正式业务系统仍是其数据的事实源。
2. **地图而非手册**。文档分层、每层只回答一个问题；新建原型的 `AGENTS.md`/`docs/README.md` 以目录索引为主，指向更深的 docs，不把所有细节塞进一个文件。已有仓库规则照常遵守。
3. **指定意图 + 建反馈回路，而非微管实现**。人写"要达成什么 + 怎么算成功"（ExecPlan + 验收），把"怎么实现"留给 agent。不变量（依赖顺序、安全边界、口径）写死并机械执行；实现细节放开。
4. **深度优先：积木解锁积木**。把大目标拆成最小可验证切片（MVS），每个切片为下一个解锁更复杂能力，按依赖链顺序推进。一次只详细实现一个切片。
5. **人掌舵，agent 执行**。人写 spec/契约/验收标准、定优先级、验证结果；agent 写代码。遇阻时不是"让 agent 更努力"，而是问"缺什么能力、护栏或 spec"，把答案补进 repo（仍由 agent 写补丁）。
6. **区分模型权威与代码权威**。模型节点只做结构化抽取或语言生成，对事实/数字/安全无权威；状态、数字计算、安全边界、副作用守卫由确定性代码节点拥有权威并机械执行。这是区别"能跑的 demo"与"可信系统"的分界。

## 流程总览（从空仓库到可验收原型）

按顺序推进，每个阶段产出固定形态的文档落进 `docs/`。模板见对应 references。

### Phase 0｜技术探针 SP-00（可丢弃）
在获准的隔离测试环境调用外部依赖（模型端点、合成数据源、测试数据库），用最小可丢弃代码验证高风险前提，**在第一个 MVS 之前完成**。探针不产生用户可见价值，不算 MVS。

### Phase 1｜PRD
What / Why / How well。必须含：业务背景、问题定义（核心问题+核心矛盾+Demo 边界）、核心用户、典型场景、用户流程、核心功能（`FR-xx` 编号，每条带 Demo 验收结果）。无法确认的内部事实标"待确认"，不虚构。模板：`references/prd-structure.md`

### Phase 2｜技术实现 Plan
架构选型、技术栈、provider/模型/数据源的**现场验证**结论、关键约束。不照搬记忆，端点和账号能力现场跑通再下笔。模板：`references/tech-plan-structure.md`

### Phase 3｜MVS-Plan
把系统切成有依赖顺序的最小可验证切片。必须含：拆分原则、切片总览表（顺序/切片/用户可观察结果/对应PRD/状态）、依赖关系图、滚动细化规则。**依赖链在此阶段定死，未排清不准动编码。** 模板：`references/mvs-plan-structure.md`

### Phase 4｜逐 MVS 实现（核心循环）
对当前唯一 MVS：
1. 写 `MVS-xx-ExecPlan.md`：当前状态、要解决的问题、调查事实、方案与边界、单元拆分、验收方式。
2. 把 MVS 拆成最小执行单元 `MVS-xx-yy`，每个单元只产出一个明确结果。
3. 逐单元让 agent 编码，写清输入/动作/预期输出/实际验证方式。
4. **当前单元未通过，不进入下一单元。**
5. MVS 以一份**可重复验收**收尾：空环境、固定输入、可复现、留证据。
6. 验收通过后标记 MVS 已完成，再细化下一个 MVS。

模板：`references/execplan-structure.md`、`references/acceptance-structure.md`

### Phase 5｜架构总览收口（最后写）
全部 MVS 完成后，回头提炼整体架构总览（带 mermaid 流程图，标注模型节点 vs 确定性代码节点的权威划分）。**不在开头写**——开头写的是想象，收口写的是事实。模板：`references/architecture-overview.md`

## 硬不变量（护栏，机械执行）

| # | 不变量 | 违反信号 |
|---|---|---|
| 1 | 已确认的原型意图/契约/验收落盘进 `docs/` | 决策只存在于对话里，repo 里查不到 |
| 2 | 新建的 `AGENTS.md`/`README.md` 以索引为主；保留已有仓库规则 | 一个新文件塞满所有约束，或覆盖原规则 |
| 3 | 依赖链在 MVS-Plan 阶段定死；前置 MVS 未完成不动后续 | 跳过地基直接写上层 |
| 4 | 任何单元编码前先有 ExecPlan | 边聊边写、无意图记录 |
| 5 | 每个单元以可重复验收收尾，未通过不进下一单元 | 写完就说完成，无隔离重建证据 |
| 6 | 架构总览在全部 MVS 完成后才写 | 项目伊始就写架构图 |
| 7 | 模型节点无事实权威，状态/数字/安全归代码节点 | 让 LLM 直接算数字或做安全判断 |
| 8 | 遇阻问"缺什么能力/护栏/spec"，补进 repo | 反复让 agent "再试一次" |

## 文档目录布局

```
docs/
├── README.md            # 目录索引（map），指向各 docs，同步维护链接
├── overview/            # 跨阶段：PRD、技术Plan、MVS-Plan、最后的架构总览
├── mvs-01/              # 一个 MVS 一个目录：ExecPlan + 单元文档 + 可重复验收
├── mvs-02/
│   └── schema-catalog/  # 阶段内持续多文档的主题建子目录
└── mvs-xx/
```

放置规则与索引维护见 `references/doc-layout.md`。颗粒度从第二个 MVS 起固定为 `MVS-xx-yy`，不再拆 `MVS-xx-yy-zz` 三级；内部清单不形成独立编号或 ExecPlan。

## 与思想武器的关系

本 skill 是工程产物生成流程，不是方法论。调查、矛盾分析等可在 Phase 1/4 的"调查事实""矛盾分析"段落内调用对应 skill，但本 skill 不负责调度它们。

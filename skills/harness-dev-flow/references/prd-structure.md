# PRD 结构模板

PRD 回答 What / Why / How well。无法确认的内部事实标"待确认"，不虚构。每条核心功能带可观察的 Demo 验收结果。

## 章节骨架

```
# <项目> PRD

## 1. 业务背景
  - 这类工作通常包含什么
  - 当前流程存在的问题（逐条列）
  - 因此需要构建什么

## 2. 问题定义
### 2.1 核心问题
  - Agent 要自动完成哪几步（编号列）
### 2.2 核心矛盾
  - 自动化 vs 必须保证真实/可核验 的张力
  - 一句话点明：最核心要解决的不是 X，而是 Y
### 2.3 Demo 边界
  - 聚焦哪条最小可验证链路（用箭头串起来）
  - 明确不做什么（不自动决策/交易/写入）

## 3. 核心用户
  - 每类用户的主要需求（逐条列）

## 4. 典型使用场景
  - 每个场景给一句真实用户输入示例
  - Agent 需要识别什么 / 输出什么

## 5. 核心用户流程
  - 编号步骤，从用户输入到成果生成

## 6. 核心功能
### FR-01 ...
  - 能力描述
  - 关键约束（如只读、安全边界）
  - 失败/无数据时如何说明
  - **Demo 验收结果：** <可观察的成功标准>
### FR-02 ...
```

## 要点
- `FR-xx` 编号会被 MVS-Plan 追踪引用，保持稳定。
- 每条 FR 的"Demo 验收结果"是后续 MVS 验收标准的源头，要可观察、可判定。
- Demo 边界越早写死越好，防止范围蔓延。

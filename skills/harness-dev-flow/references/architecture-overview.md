# 架构总览收口模板

全部 MVS 完成后才写。开头写的是想象，收口写的是事实。聚焦"整条链路中最核心、最区别于普通实现的一段"，放大其内部细节。

## 章节骨架

```
# <核心段> 结构化详解

> 本文聚焦整个流程中最核心的一段：<一句话>。
> 前面所有流程在做什么准备；后面所有流程在做什么收尾。
> 中间这一段是唯一真正<拿到数据/产生核心价值>的环节。

## 一、整体流程图
  mermaid flowchart，节点颜色编码：
  - 橙色 = 模型节点（只做结构化抽取或语言生成，无事实权威）
  - 蓝色 = 确定性代码节点（拥有状态/数字/安全权威）
  - 绿色 = 存储
  - 红色 = 失败或中断终态

## 二、节点逐详解
  每个节点一个 subgraph：
  - 输入是什么（来自上游的确定产物，不是重新理解）
  - 是模型节点还是代码节点（谁有权威）
  - 输出是什么（确定性、可复现、内容寻址）
  - 失败时进入哪个终态 / 是否可重试

## 三、重试循环
  - 可重试失败如何转成 repair feedback
  - feedback 是白名单字段，不含原始 SQL/错误详情（防泄漏）
  - 最多重试次数

## 四、权威划分说明
  - 模型节点：只抽取/生成，对事实/数字/安全无权威
  - 代码节点：状态、数字计算、安全边界、副作用守卫的权威来源
  - 为什么这样分：模型可能出错，仍要保证结果正确/安全/可追溯
```

## 要点
- 流程图必须标注节点权威类型，这是本流程的核心设计原则（Harness 原则 6）。
- "输入是上游确定产物，不是重新理解"要写明--避免每步都让模型重新理解问题。
- 失败终态和可重试失败要区分清楚。

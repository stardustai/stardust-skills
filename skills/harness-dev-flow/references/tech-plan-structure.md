# 技术实现 Plan 结构模板

技术 Plan 把 PRD 落到具体技术决策，所有 provider/模型/数据源/数据库能力**现场跑通再下笔**，不照搬记忆。灵感来自 Harness 的"boring tech 更易被 agent 建模"。

## 章节骨架

```
# <项目> 技术实现 Plan

## 1. 实现目标
## 2. 核心技术决策
### 2.x 为什么不能让模型直接 <危险动作>   ← 每个关键决策写清"为什么"
## 3. Demo 场景与数据方案
### 3.1 选择的业务场景
### 3.2 主数据源                  ← 现场验证的字段、分页、限流、Attribution
### 3.3 Demo 数据规模
### 3.4 非结构化资料
### 3.5 数据源不可用时的兜底
## 4. 总体架构
## 5. Agent 编排设计
### 5.1 编排原则
### 5.2 主执行图                ← mermaid
### 5.3 节点职责                ← 标注模型节点 vs 确定性代码节点
### 5.4 State：运行中的可变事实
### 5.5 Runtime：一次执行的环境
### 5.6 Context：真正送入模型的信息   ← 三者不要混成 Memory
### 5.7 Checkpoint：只解决会话连续性
### 5.8 Message：对话记录 ≠ 业务状态
### 5.9 并行、重试与终止
## 6. <安全执行链>              ← 副作用/只读/越权守卫
## 7. 数据库设计
## 8. 结果可信机制              ← 证据账本、Claim 校验、输出规则
## 9. 模型接入方案              ← 现场验证的端点/Model ID/限流/错误格式
## 10. 后端与前端范围
## 11. 建议目录结构
## 12. 三阶段实现路线            ← 与 MVS-Plan 衔接
## 13. Demo 验收标准
```

## 要点
- State / Runtime Context / Checkpointer / Store 是四个不同概念，别混成 "Memory"。
- 模型端点、账号能力、限流格式必须现场验证后记录，不能凭模型名推断。
- "为什么不能让模型直接 X"这种权衡段落是后续护栏的依据，要写清。

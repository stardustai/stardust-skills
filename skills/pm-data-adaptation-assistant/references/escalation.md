# 升级边界

先判断问题风险。凡是下列场景，PM 可以先收集材料，但不能让 skill 直接下最终结论。

## 必须升级给开发

| 场景 | PM 可以先做什么 | 回答口径 |
| --- | --- | --- |
| 真实平台导入或导出失败 | 收集完整报错、截图、项目/任务/池子 ID、输入路径、输出路径、发生时间、失败阶段 | 不能直接判断是脚本问题，要先定位是数据、平台配置、权限、模板还是脚本输出 |
| 平台提示 `uuid`、`uniqueIdentifier`、`操作项不存在`、`节点顺序不一致`、`annotation 与操作项不匹配` | 收集报错原文、失败 JSONL 样例、当前项目模板/操作项信息、数据来源项目和目标项目 | PM 可以按类型解释大概含义，但根因和修复方案必须开发对比数据与模板后确认 |
| 客户格式、客户术语、交付口径不清 | 收集客户原文、样例文件、字段说明、验收要求、历史交付样例 | 这是交付口径问题，必须开发或项目负责人确认 |
| 需要修改脚本、参数默认值或部署包 | 写清需求、样例、期望输出和影响范围 | PM 不能只凭经验要求上线，开发要确认脚本路径、运行环境和验证范围 |
| 只有本地语法检查、mock 或离线样例 | 标注当前验证方式 | 只能说本地检查通过，不能说生产可用或可直接交付 |
| 导出结果要发给客户 | 准备数量校验、抽样结果、格式对照、客户样例、风险点 | 工具跑完不等于可交付；校验不足时必须转开发确认 |
| 涉及 AK/SK、Token、内网地址、客户隐私数据 | 不要在群聊或 skill 中粘贴敏感内容 | 只描述问题类型，敏感值由开发在安全环境中查看 |

## 回答时禁止

- 禁止直接说“就是脚本问题”。
- 禁止说“可以直接交付客户”，除非已有明确验收和开发确认。
- 禁止承诺远端 OSS、平台、部署包、模板配置已经生效，除非当前已验证。
- 禁止把客户项目名、内部地址、凭据、完整路径当作通用知识写进回答。

## 推荐收口句

- "这类问题需要开发确认根因，你先把这些信息整理好。"
- "按历史口径可以先这样理解，但当前批次是否适用要看样例和配置。"
- "工具完成只代表流程跑完，是否交付要看校验结果。"
- "这个问题 PM 可以先排除信息缺失，但不能自行定最终映射。"
